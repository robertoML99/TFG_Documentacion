Una vez definidos el conjunto de datos del que se parte y las nuevas características con las que se va a enriquecer este, es momento de explicar cómo se realizó el proceso para construir el conjunto de datos final utilizado en el entrenamiento y evaluación del modelo de aprendizaje automático.

Como se mencionó en la sección \ref{SEC:BASEEX}, la base experimental consta de ficheros PCAP que contienen los paquetes del tráfico en bruto y ficheros CSV en los que estos paquetes han sido procesados, agrupados en flujos y para los que se han extraído características. Para procesar estos PCAP, se desarrollaron una serie de scripts en Python que, utilizando la herramienta \texttt{tshark}, extraen la información necesaria de los paquetes para poder reconstruir los flujos y obtener las características definidas en la sección \ref{SEC:NEW_FEAT}.

Se escogió Python como lenguaje de programación debido a su simplicidad y al gran número de librerías disponibles para el procesamiento de datos. En cuanto a \texttt{tshark}, es la versión en línea de comandos de \texttt{Wireshark}. Se utiliza para extraer información de ficheros PCAP sin interfaz gráfica. En este caso, se utiliza para extraer la información de los paquetes de tráfico IP cuyos protocolos de transporte son TCP o UDP. A partir de cada paquete se obtiene la dirección IP origen, dirección IP destino, puerto origen, puerto destino, un id para el protocolo de transporte (6 para TCP y 17 para UDP), la longitud del paquete, la pila de protocolos por los que pasa el paquete y el contenido del payload en hexadecimal. 

Se desarrollaron un total de 5 scripts, uno por día. La lógica general es parecida en todos, pero los ficheros de entrada tenían cada uno sus peculiaridades. El lunes requirió un tratamiento especial para enlazar los flujos construidos en el script con los del fichero CSV de base, ya que en algunos casos el ID del flujo estaba invertido. Los scripts de martes y miércoles no requirieron de modificaciones ya que tenían un único fichero CSV cada uno y se pudieron unir a sus respectivos CSV directamente. Los casos de jueves y viernes requirieron un tratamiento especial también, ya que partían de un único PCAP pero en el material de partida tenían múltiples CSV asociados, separados por distintos tipos de ataques. Además, en el del jueves se requirió normalizar los datos de uno de los CSV debido a inconsistencias en el formato.

La lógica de extracción y procesamiento de datos de estos scripts se puede agrupar en 4 etapas comunes: extracción de los campos desde los PCAP, reconstrucción de los flujos, cálculo de las nuevas características e integración de las nuevas características en el conjunto de datos de partida.

En primer lugar, cada script invoca la llamada a \texttt{tshark} sobre el fichero correspondiente, extrayendo los campos mencionados para cada paquete. Estos se guardan de forma tabular mediante la librería \texttt{pandas} para que queden bien estructurados.

Posteriormente, se realiza un preprocesamiento de los campos extraídos previo al cálculo de las nuevas características. Más concretamente, se convierten a formato numérico la longitud del paquete, el tiempo relativo de captura y los puertos TCP y UDP. A partir de los puertos TCP y UDP se obtienen los puertos de origen y destino efectivos, además del protocolo de transporte unificado. Una vez hecho esto, se construye el identificador de flujo en formato IP origen–IP destino–puerto origen–puerto destino–protocolo.

Una vez construido el identificador, los paquetes se agrupan por flujo. Una vez se tienen los flujos, se extrae el payload de cada paquete cuando estos tengan un payload válido. Sobre estos bytes se calculan las características definidas en la sección \ref{SEC:NEW_FEAT}, tanto a nivel de paquete como de flujo dependiendo de qué característica se esté obteniendo.

Finalmente, las nuevas características calculadas se integran en los ficheros CSV mediante el identificador de flujo. Dependiendo del día de captura, se integra de forma directa (martes y miércoles), con un segundo intento con el identificador invertido (lunes) o iterando sobre los distintos CSV que componen ese día (jueves y viernes). Para comprobar que se agruparon los paquetes de forma correcta y que cada flujo original fue enriquecido correctamente, se incluyó una característica booleana auxiliar, \texttt{NewFeat\_Matched}, cuya función consiste en indicar si los flujos originales del conjunto de datos encontró una correspondencia con los flujos calculados en los scripts. Para todos los ficheros CSV resultantes, la proporción de \texttt{NewFeat\_Matched} con valor $True$ fue superior al 99\%, confirmando que el conjunto de datos se enriquece correctamente para la mayoría de flujos.

Una vez generados los ficheros enriquecidos para cada uno de los días se unifican en un solo fichero. Para ello, se desarrolló un script de Python que filtraba aquellos flujos en los que $\texttt{NewFeat\_Matched} = True$. Esto genera un único conjunto de datos en los que todos los flujos que aparecen han sido mejorados con las características añadidas. Posteriormente, se elimina la columna \texttt{NewFeat\_Matched}. Este fichero final es el que será utilizado para el entrenamiento y evaluación del modelo de aprendizaje automático.

Si se observa la presencia de las distintas clases en este conjunto final, se puede ver que el conjunto está desbalanceado. Más concretamente, hay clases con decenas de muestras y otras con cientos de miles o incluso millones como el tráfico benigno. Esto se tendrá en cuenta a la hora de entrenar el modelo como se va a explicar en la próxima sección.
